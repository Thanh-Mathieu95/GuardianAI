# Architecture and deployment boundaries

The app runs on one continuous Node.js 24 process. Next route handlers own signed HttpOnly sessions, same-origin checks, token invitations and schema validation. Each account's mutations are queued; the repository rejects stale revisions. SQLite transactions commit account state, record-chain updates and staged audio together. PostgreSQL uses the same SQL contract and row locks; the adapter has not yet been exercised against a hosted database.

`lib/engine.ts` is the source of truth. Replies contain original quotations. Admission checks precede AI selection. Selected IDs must refer to eligible offers. AI errors fall back to bounded rules; live routing errors never fall back to synthetic geometry. The accepted destination stays stable until its constraints or route become invalid. Monitoring expires commitments, marks unanswered requests, checks route deviation and stops guidance after 90 seconds without GPS. Check-in deadlines and demo deadlines are persisted and evaluated by a two-second server timer.

Only one server instance should run this coordinator. The timer and request limiter are process-local. Scale-out needs a distributed work queue and rate limiter. Vercel functions alone are unsuitable for continuous monitoring: host the complete Node server, or use a separate frontend with `GUARDIAN_BACKEND_ORIGIN` set during its build. In that split setup, `PUBLIC_URL` on the backend must equal the frontend HTTPS origin and both services must use compatible routes/cookies.

On an internet deployment set a stable random `SESSION_SECRET`, exact HTTPS `PUBLIC_URL`, `AI_ACCESS_CODE`, server-side `OPENAI_API_KEY`, optional Google Routes key and persistent storage. The AI code gates activation for demo participants. Keep it private; it is not a replacement for production identity, per-user billing controls or abuse protection. When `PUBLIC_URL` is set without an AI access code, paid AI stays disabled. Set `GUARDIAN_BIND_HOST=0.0.0.0` only on the hosted service. Local startup binds to loopback by default.

Audio is opt-in and split into chunks; retries must match their original bytes, sequence and MIME type. SHA-256 hashes use the raw bytes. Record revisions form a hash chain. These hashes detect modification relative to their saved references; they are not external notarization and cannot prove the truth of a statement. An operator able to rewrite the entire database could rewrite the chain. Retention and off-site encrypted backup policy must be defined before real deployment.

Invitations are bearer credentials; only token hashes are stored. Contacts see a session after being included in its recipient list. Partners do not see the walker's precise location before acceptance. Owners can read their records and audio; joined contacts obtain the current report after signal loss. The current preview shares report metadata, not a downloadable audio attachment, with contacts. Record deletion is atomic and invalidates the old record chain; it does not revoke copies a recipient already downloaded.

Real recipients must keep their page open. No SMS, PSTN calling, native push or emergency dispatch service is included. Browser GPS and timers may pause when a phone locks. This implementation supports supervised demonstrations, not a guarantee of protection or an emergency response network.


The in-app call extension is described in [IN-APP-COORDINATION.md](IN-APP-COORDINATION.md). Call records, event deduplication, attempts, deadlines, transcripts and partner profiles are stored in the same versioned account payload and hash-chained incident snapshots. Separate signed demo/live owner cookies isolate their incidents and member lists. No telephone gateway was added.
